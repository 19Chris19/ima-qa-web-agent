# 多客户会话与 IMA 账号池运行方案

日期：2026-08-02

## 1. 目标

让一个 IMA 登录账号可以长期承载多个客户会话，同时满足：

- 每个客户拥有自己的会话和上下文。
- 客户追问时继续使用原来的 IMA session。
- 客户没有明确新建会话时，不自动切断上下文。
- 不同客户的问题、历史、来源和答案不能互相串联。
- 账号数量增加后，可以通过调度提高总吞吐量。

这里要区分两个概念：

```text
一个账号可以绑定多个客户 session
不等于一个账号可以无限并发处理多个问题
```

当前验证结论是：每个账号 1 路 active ask 稳定；同一账号 2 路并发已经出现“提问太快啦”和网络失败。因此默认仍按“每账号 1 路”运行，多 session 先承担会话归属和排队，不直接突破 IMA 的账号级限制。

## 2. 核心对象

```text
客户身份 clientId
    -> 会话 conversationId
        -> IMA 账号 accountId
            -> IMA 上游 sessionId
```

### 客户身份

客户身份由客户网站登录用户映射而来。浏览器直连使用 HttpOnly `ima_qa_client_id` cookie；客户后端代理使用稳定的 `X-IMA-Client-Id`。

同一个网站用户可以有多个会话，但不同网站用户不能共用同一个 client ID。

### 会话 conversationId

`conversationId` 是服务端生成的随机 ID，代表一个可持续追问的聊天线程。服务端保存：

- 所属 client ID
- 创建和更新时间
- 过期时间
- 最近若干轮问答
- 粘滞的 IMA `accountId`
- 粘滞的 IMA `sessionId`

当前默认保存 7 天、最多 12 轮、最多 5000 个会话。

### IMA sessionId

IMA `sessionId` 是上游知识库 Agent 的上下文。客户第一次提问时创建；后续追问继续传同一个 ID。它不能在账号 A 和账号 B 之间随意迁移。

## 3. 正常生命周期

### 3.1 第一次提问

```text
客户提交问题
    -> 服务端确认 clientId
    -> 创建 conversationId
    -> 账号池选择空闲账号
    -> 为该账号初始化 IMA session
    -> 保存 accountId + sessionId
    -> 流式返回答案和 conversationId
```

浏览器把 `conversationId` 保存到本地；客户后端代理保存到自己的用户会话中。

### 3.2 普通追问

```text
客户提交追问 + conversationId
    -> 校验 clientId 是否匹配
    -> 读取服务端历史
    -> 读取绑定的 accountId + sessionId
    -> 继续使用原 IMA session
    -> 保存新的一问一答
```

只要客户没有明确新建会话，就不重新分配账号，也不重新创建 IMA session。

### 3.3 明确新建会话

中转界面应提供“新建会话”按钮。点击后：

1. 调用 `POST /api/conversations`，或者清除当前会话 ID 后发送第一问。
2. 前端清空当前聊天显示和本地 `conversationId`。
3. 新会话由账号池重新选择账号。
4. 新会话拥有新的 IMA `sessionId`。

新建会话不会删除旧会话。旧会话按 TTL 自动过期，也可以提供“删除会话”操作。

### 3.4 会话结束

会话可以因为以下原因结束：

- 客户主动删除。
- 超过 TTL 未使用。
- 达到存储数量上限，被最旧会话淘汰。
- 绑定账号永久失效，维护者要求客户新建会话。

## 4. 账号池调度

### 新会话

新会话在可用账号中采用 LRU 调度：

- 账号未禁用。
- 账号不在冷却期。
- 当前 active ask 未达到账号并发上限。
- 最近使用时间最早的账号优先。

### 已有会话

已有会话必须回到原账号：

```text
conversation-A -> account-1 -> session-A
conversation-B -> account-1 -> session-B
conversation-C -> account-2 -> session-C
```

多个客户可以绑定同一个账号，但在当前安全配置下，同一账号的 active ask 串行执行。账号空闲后，再处理下一个绑定会话。

### 同一会话并发

同一个 `conversationId` 同时收到两条问题时，第二条返回 409。原因是两条消息不能同时写入同一个 IMA session，否则上下文顺序和答案归属都不可靠。

## 5. 并发模型

当前模型：

```text
每账号 active ask 上限 = 1
总 active ask = 可用账号数
```

未来实验模型：

```text
每账号 active ask 上限 = N
总 active ask = 可用账号数 × N
```

但 `N` 必须通过真实 IMA 测试得到，不能由本地服务自行假定。单账号 2 路测试已经出现不稳定，因此当前不建议把 `N` 直接设为 2。

队列只是等待区，不代表真实吞吐量。请求总数、平均完整回答耗时和 IMA 账号级限流共同决定实际承载能力。

## 6. 历史记录与用户体验

### 当前已经具备

- 服务端持久化最近问答历史。
- 追问时使用服务端历史，不信任调用方传来的任意 `history` 覆盖上下文。
- 页面当前打开期间可以连续显示完整聊天。
- 服务重启后可以恢复会话元数据、账号绑定和 IMA session 绑定。
- `GET /api/conversations?limit=50` 返回当前客户的会话摘要列表。
- `GET /api/conversations/:conversationId` 返回当前客户的扁平消息历史和精选来源。
- 主页面与 `embed.html` 都支持新建、切换、删除、刷新恢复和移动端会话抽屉。
- 历史每轮最多保留 10 条脱敏来源；旧的无来源记录仍可读取。

### 本阶段边界

阶段二只补历史和中转界面，不改变双账号、每账号一条 active ask 的稳定基线。运营指标、账号级并发实验、跨进程锁和 Redis/PostgreSQL 迁移仍留在后续阶段。历史读取接口只能返回当前 client ID 所属会话，不能提供全局会话查询。

## 7. 故障处理

### IMA session 过期

优先在原账号上重建一次 session，并更新当前会话的 `sessionId`。这样不改变客户归属，也不改变账号。

### 账号刷新或短 token 过期

账号内部使用 refresh lock，多个请求同时发现快过期时只执行一次刷新。刷新后的登录态安全写回 runtime 文件。

### 账号限流

账号进入 cooldown：

- 暂停为新会话分配该账号。
- 已绑定该账号的会话不迁移到其他账号。
- 客户收到稍后重试提示，避免上下文错接。
- 冷却结束后账号恢复可调度。

### 账号永久失效

账号从可用池摘除。已有会话不能自动迁移；客户需要新建会话。后续如果要支持迁移，必须先把服务端历史压缩成新账号可接受的上下文，并单独标注“上下文重建”，不能伪装成原生 session 延续。

## 8. 安全边界

- `clientId` 和 `conversationId` 双重校验。
- 不允许前端指定知识库 ID。
- 不向前端返回 Cookie、refresh token、API key。
- 会话文件权限保持 `600`，不提交 Git。
- 不允许所有客户共用一个 `X-IMA-Client-Id`。
- 管理接口与问答接口分开鉴权。
- 单会话串行，账号级限流，服务级队列和超时同时生效。

## 9. 推荐落地顺序

### 阶段一：保持当前稳定基线

- 两个账号，每账号 1 路 active ask。
- 多个客户 session 可以绑定同一账号并排队。
- 继续验证多轮上下文和账号冷却行为。

### 阶段二：补齐中转界面

- 新建会话。
- 会话列表。
- 历史恢复。
- 删除会话。
- 会话状态和错误提示。

### 阶段三：做单账号并发实验

每个账号单独测试 1、2、3 路不同 session，记录：

- session 创建成功率。
- 首字延迟。
- 完整回答耗时。
- 429 / “提问太快啦”比例。
- 5xx 和网络失败比例。
- 是否出现跨 session 内容。
- 冷却恢复时间。

任何跨 session 内容都属于立即停止条件。只有连续多轮、多个批次稳定通过后，才考虑把单账号并发上限从 1 调到 2。

### 阶段四：扩大账号池

优先增加合法加入同一共享知识库的账号数量。账号池增加比强行提高单账号并发更可控；超过单实例规模后，再把会话和租约迁移到 Redis 或 PostgreSQL，并增加分布式锁。

## 10. 目前仍未完全摸清的问题

1. IMA 对同一账号同时创建和使用多个 session 的硬上限没有公开、稳定的官方说明。
2. “提问太快啦”是账号级、IP 级、session 级还是综合风控，仍需分时段和不同账号继续测试。
3. IMA session 的真实有效期、服务重启后的可复用边界，需要长期观测。
4. 账号 refresh 后，旧 session 是否始终有效，当前只做了有限验证。
5. 客户网站登录态与 `X-IMA-Client-Id` 的正式映射方式，需要结合实际接入方的鉴权系统确定。
6. 多进程或多副本部署不能继续使用本地 JSON 作为唯一会话锁，需要在扩容前完成共享存储改造。
7. 历史消息的隐私保留期限、删除证明和管理员审计范围，需要根据实际客户场景确定。

## 11. 一句话结论

一个 IMA 账号可以绑定多个客户 session；每个客户的追问继续使用自己的 session，历史也按客户和会话隔离。当前真正的瓶颈不是 session 数量，而是同一账号的 active ask 能力。因此现阶段采用“多 session 归属 + 单账号串行轮流处理”，再用真实压测决定是否逐步开放单账号多并发。

## 12. 规模未知时的上线预期与长期路线

### 先回答“这是不是长效方案”

会话控制面是长效方案：`客户身份 -> conversationId -> accountId -> sessionId` 这条归属关系、历史保存、会话锁、账号路由和可观测性，未来不论接 IMA Web、IMA OpenAPI、本地 RAG 还是别的正规模型通道，都可以继续复用。

但把 IMA Web 私有接口和网页登录态作为唯一容量来源，不是可承诺无限扩展的长期方案。它的风险来自上游账号限流、登录态、网页协议变化和账号风控，而不是本地代码能完全消除的问题。因此长期目标应是“可替换 Provider 的会话控制面”，IMA Web Agent 是当前高质量通道，而不是唯一容量承诺。

### 不用注册用户数估算容量

注册用户、日活用户和同时提问用户不是同一个指标。真正决定容量的是：

```text
峰值请求率 = 峰值同时提问数 ÷ 平均完整回答耗时
```

当前两个账号、每账号 1 路 active ask 的安全上限是 2 路同时上游问答。实测单问完整耗时约 10 至 19 秒；在不考虑上游波动的理想情况下，对应约 6 至 12 条/分钟。上线预估应保守按 4 至 8 条/分钟看待，并持续以 P95 完整回答耗时和 IMA 限流比例校准。

一个账号可以保存很多客户 session，但这只提高“可服务的客户数量”，不提高同时完成问答的能力。低频客户可以很多；高峰时同时提问的客户数才是容量边界。

### 阶段预期

| 阶段 | 推荐配置 | 适用场景 | 上线闸门 |
| --- | --- | --- | --- |
| 阶段 0：内部验证 | 2 账号、2 路总并发 | 维护者和小范围真实问题验证 | 多轮不串线；登录刷新可恢复；连续多天无严重错误 |
| 阶段 1：受控试用 | 2 至 5 账号、每账号 1 路 | 有限邀请用户、低频问答 | 记录峰值请求率、P95 耗时、429/冷却率；队列不长期堆积 |
| 阶段 2：稳定小规模上线 | 3 至 5 账号、独立会话存储和运营监控 | 网站真实用户开始增长 | 明确客户身份映射；历史读取/新建会话完成；故障告警和容量报表可用 |
| 阶段 3：规模化决策 | Redis/PostgreSQL + 多实例 + 可替换 Provider | 峰值超过单机单账号池可承受范围 | 不能只增加账号；必须验证上游政策、成本、合规、降级 Provider 和分布式锁 |

阶段 1 和阶段 2 不应对外承诺固定“支持多少注册用户”。只有连续采到至少一周的真实峰值数据后，才能以峰值同时提问数和 P95 时延给出服务等级预期。

### 每个阶段必须回答的容量问题

上线前和每次扩容前，维护者需要填写以下问题：

1. 峰值 5 分钟内有多少条真实提问、其中多少条是追问？
2. P50/P95 首字延迟和完整回答耗时分别是多少？
3. 每个账号的成功率、429/“提问太快啦”比例、冷却次数是多少？
4. 队列最大深度、超时比例、客户主动取消比例是多少？
5. 新建会话和旧会话追问的比例是多少？
6. 当前账号、服务器和 Provider 的月度维护成本是多少？
7. IMA Web 通道不可用时，用户看到什么降级行为，业务是否能接受？

这些问题就是后续的容量接口：没有数据时不盲目扩账号或调大并发，有数据时再决定增加账号、优化缓存，还是启用官方/API/本地 Provider。

### 建议的升级闸门

- 队列经常超过总并发的 3 倍，先增加合法账号或限制入口流量。
- P95 完整回答超过 60 秒，先检查 IMA 上游、SSE 反代和账号冷却，再谈提升并发。
- 任一账号的限流或网络失败持续超过 5%，保持每账号 1 路，不开放单账号多并发。
- 超过 5 个账号、需要多进程或多台机器时，把会话和锁迁移到 Redis/PostgreSQL。
- IMA Web 出现连续协议变更、登录维护成本不可接受或业务需要稳定 SLA 时，不能再把它作为唯一 Provider。

### 当前最现实的路线

先以两个账号、两路总并发完成受控试用，收集真实问题量和时延。随后优先补齐历史恢复、新建会话、会话列表和运营指标；需求增长时优先增加合法账号，而不是强推单账号并发。Provider B 或本地 RAG 可以继续作为长期独立性建设，但在质量和容量被验证前，不应承诺它们替代 IMA Web Agent。
